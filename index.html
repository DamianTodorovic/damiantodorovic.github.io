      Next — three ways in, one ranked answer→

      Three ways in, one ranked answer.

      Full text, meaning and connection are searched at once, fused into one ranking, and re-ranked on your machine. Nothing is sent away — the vector leg runs on a local model through Ollama, and without it the engine still answers, lexically.

      Full text

      Exact words

      BM25 finds the phrase you actually used: the name, the number, the reference.

      Meaning

      Close enough

      Vector similarity finds the note that says it differently — embeddings run through a local model, so meaning never needs a cloud call either.

      Connection

      Linked in

      The graph leg matches your query against the entities in the knowledge graph, so a name brings the notes that carry it.

      Fusion

      One ranking

      The three are fused with Reciprocal Rank Fusion, then re-ranked locally by term coverage, phrases, title and tags.

        Read the bottom strip the way the fusion reads it: each column is one leg’s own order, and a note starts with 1/(60+rank) from every leg that returned it — so a note that wins no first place can still top the fusion, which is the whole argument for running three. The percentage on a card is the other half: the reranker’s own read of that one note against your question — term coverage, title hits, an exact phrase — which nudges the fused order by up to a quarter. Three things stand in for the server here: hashed character trigrams replace the local embedding model, the entity leg reads capitalised names and acronyms out of your lines where the engine runs the full extractor, and the text leg is a hand-written Okapi BM25 — the same formula and the same k1 1.2 and b 0.75 the server asks SQLite for, over a stemming tokenizer where SQLite does not stem. The fusion and the reranker are the engine’s own code, ported. What this page does not run is the rest of the pipeline: the recency, confidence and retention boosts the server multiplies in, and the policy gate that withholds a note at the last step.

        Frequently asked

        01

        How do I run KEPTA?

        Two ways. The desktop app: download the DMG for your Mac from the release page, drag it into Programs, right-click → Open once (ad-hoc signed — macOS asks a single time, then never again). Or one command: npx kepta-mcp — the memory comes up on your machine and every MCP client (Claude Desktop, Claude Code, Cursor, Windsurf) shares it. There is also a Python client (pip install kepta) and a headless HTTP API.

        02

        Why not just a database?

        A database answers questions you already designed a schema for. This is the other case: you write the sentence the way you would say it — "Mara moved the Q4 close to 12 November" — and the engine decides the shape. It pulls the entities and the links out of the prose, files the note under a type, and keeps two clocks: when the fact was true and when you learned it. That second one is what a row cannot do. An UPDATE overwrites what you believed, so a question about March returns today's answer; here the old validity stays, which is why "what did I know on 3 March" is a question you can ask at all. Above the storage sits the retrieval: three legs fused with reciprocal rank fusion, re-ranked locally, measured leg by leg in the Evidence section. If your data does have a schema you control, use a database — it is quicker, and KEPTA would be the wrong tool for you.

        03

        Is it really free?

        Yes. The engine is source-available under BUSL-1.1 and free forever — running it in your own organization is always allowed. There are no tiers inside the memory: everything that makes it smart is in the free engine.

        04

        Where do the benchmark numbers come from?

        Two commands in the public repository. npm run eval scores the engine against a fixed 58-note corpus with 45 queries, offline, deterministic and without embeddings: Hit@1 71.1% and MRR 0.759, against 51.1% and 0.559 for the naive substring search it replaces. npx tsx scripts/ablation.ts adds local embeddings from a running nomic-embed-text and measures each retrieval leg separately; the fused engine returns a result on all 45 queries where full-text alone comes back empty on 4. The corpus, the queries and the relevance judgements are all in the repository, so you can rerun both and disagree with them.

        05

        What happens to my data?

        It never leaves your machine. One SQLCipher-encrypted file, keys in your OS keychain, no telemetry, no cloud, no account. Marking a note private in the desktop app gives it the scope private, and the source-available core enforces that at the agent boundary: memory_search and memory_list filter private notes before an assistant ever sees them. memory_graph carries the same floor onto what is derived from those notes: an entity node drops when every note naming it is private, and a relation drops with its private carrier or with either endpoint — what stays visible is a name an open note also uses, because on this machine it is not a secret. The tool returns entity names and relations, never note bodies. The owner's own channels (the app's browser, search, graph view, export) deliberately show everything, because the app has to display your own notes. And private separates the agent channel from the owner channel — it is not access control against a process running as you on your machine. Stated here because you will find it in ten minutes of reading the code, and the rest of this page is only worth as much as that sentence.

        06

        What is KEPTA Enterprise?

        The same engine as an organization infrastructure: tenant memory for many people and agents, an append-only audit journal, human review for agent writes, point-in-time recovery, role-scoped agent keys and per-tenant encryption keys. Deployed as containers on your own hardware, air-gapped if you need it. Licensed by agreement; write to me on LinkedIn.
