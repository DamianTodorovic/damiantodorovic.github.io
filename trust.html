KEPTA Enterprise — Trust Center

The open architecture answer, instead of certificate seals.

Every claim on this page is either readable in the public code or demonstrable in the app — and where it is neither, this page says so. The threat model we removed is the one a hosted product cannot remove: the cloud itself.

The principle

Other vendors document how well they protect your data while transporting it into their datacenter. KEPTA Enterprise never transports it: an organization's brain lives in encrypted files on machines the organization controls. There is no vendor access path, so there is no vendor access to answer for.

For procurement: the strongest data argument is an architecture test — "show me the path through which a client's matter leaves your building." Ours ends at your own network card.

Encryption, layer by layer

LayerMechanism
Data at restSQLCipher 4: AES-256 plus an HMAC-SHA512 over every page, WAL included
Per tenantEvery tenant brain gets its own key — derived from the master and the tenant id — and its own database file. One leaked tenant key never opens the others. The caveat we would rather state than hide: the derivation hangs on a single master key, so a leaked master opens every tenant.
Key custodyThe desktop app keeps its key in the operating-system keychain. The enterprise server reads its master key from the environment (systemd credential, secret manager, operator’s choice); a BYOK/KMS adapter is on the roadmap, not in the box today.
TransportThe console binds to loopback by default; pointing it at an interface is an explicit, warned choice, and the origin and host guards stay in front of it either way. Deployments sit behind your firewall or run air-gapped.

Append-only audit journal

Every authenticated request to the console — reads included — appends one line to a local journal: actor, action, resource, timestamp, in the order it happened. Every write and every agent call in the desktop app does the same. Each line carries the SHA-256 digest of the line before it, so removing or rewriting an earlier entry breaks the chain, and both the app and the console recompute the whole chain on one click. It is the record you hand a client, and it is what lets the console show intent against outcome. Two things it does not do, said plainly: the line records the request, not the status code it got — and a request that never authenticated never reaches the journal at all. In the source-available engine the journal is a seam, not a default: AuditSink is shipped and documented, and it is the app and the console that wire it, so a bare engine process writes no journal until you wire one.

Human review for agent writes

Writes run through a per-tenant write policy: auto, or one of the two human-gated modes review and approve, where nothing enters the brain until a person with the right scope releases it from the queue. The console shows “The AI wanted → what happened” — intent versus reality, with actor, resource and timestamp in the journal. The honest scope: what the gate executes today is note writes, and every gated call says where it stands — a verb the tenant executor does not wire yet comes back labelled not-wired-yet instead of pretending to have taken effect.

Point-in-time recovery

Every note carries the window it was true in — created, superseded, deleted — so a past state of a brain is read from the rows themselves instead of replayed from a log, and the engine answers as-of queries out of that window. A restore in the console is a confirmed rollback to a verified backup snapshot: the catalog lists each backup with its manifest count and SHA-256, the restore re-verifies the manifest before it copies, it touches only that one tenant’s directory, and the audit chain is never rolled back with the data. What is not there yet, in the console: the as-of view over the notes themselves — the timeline it steps through today is the audit view, and the engine-side as-of view follows with the engine wiring.

§203 StGB — professional secrecy (law firms, tax advisors, physicians)

  • Tenant separation: each client's brain is its own encrypted file under its own derived key, and a bound agent key reaches only the tenant it is bound to — every tenant-scoped route in the console, search and the audit trail included, sits behind that one wall. It is contract-tested: a foreign tenant id returns 403, and sharing across tenants takes an explicit, revocable grant an admin sets
  • Confidentiality levels: per tenant in the console, per note in the engine and the desktop app — a private scope that the agent channels memory_search and memory_list filter out before an assistant ever sees a result, and that memory_graph carries onto derived data, where an entity node drops once every note naming it is private and a relation drops with its private carrier. §203-grade profiles that combine both are on the roadmap, not shipped
  • No third-party leak: no KEPTA cloud, no telemetry, no third-party service in the memory path — your assistant talks to the local file, and only to the local file. The storage layer itself is third-party open source (SQLCipher through better-sqlite3-multiple-ciphers), which is the point: the code that touches your data is readable, not just promised

GDPR

  • Data subject rights: access and erasure run against local stores — there is no upstream processor to file requests with. Erasure is staged, and the stages are separate calls: a note first goes to the trash with its timestamp kept, so the act itself stays traceable, and the hard delete that drops the row together with its chunks and vectors is an explicit second step (DELETE /api/memories/:id?permanent=1, or memory_delete with permanent: true). Say the agent-side plainly instead of prettifying it: an agent can hard-delete, and memory_forget by default marks a note expired rather than trashing it — what neither can do, inside the tools it is handed, is delete the journal line its own deletion wrote. One gap we know of and are closing: graph edges carry a note id without a foreign key, so an edge’s text can outlive the row it pointed at
  • Processor status: in the standard architecture we are not a processor, because we never receive your data
  • Data residency: the strictest residency proof is machine ownership — your firm, your server, your country

HIPAA / BAA — our position

We do not sell a Business Associate Agreement wrapper. In a standard self-hosted deployment no protected health information is ever handed to us — it never leaves your building — so there is no data flow for us to contract over. That is an architectural statement, not legal advice; your compliance officer should read the deployment model the way they read any other vendor’s. Organizations whose checklists demand a BAA get the same answer as for SOC 2: the architecture removes the need for the wrapper, and we deliver the architecture proof instead. Managed options on request, under separate agreement.

Certificates (SOC 2 / ISO 27001)

A SOC 2 or ISO 27001 audit attests an organization’s operating processes — on-premise vendors hold them too, so the paper is not a cloud tax and we will not pretend it is. What we do not have today is the audit itself: KEPTA is built by one person in a source-available repository, and an annual Type II engagement is a line item we have not bought yet. Until then the offer is the architecture proof instead — access, encryption, audit and integrity controls are built into the product, the engine-side of them is readable and tested in the public repository, and the audit chain verifies itself in one click — plus a SOC 2 readiness checklist on request for procurement.
